# Acceso y sesiones

## Estado y alcance

El backend implementa autenticación real con **jose 6.2.13**, **bcrypt 6.0.0**, PostgreSQL y cookies. La migración inicial está aplicada a la base configurada en `apps/api/.env`. No se crearon usuarios ni seeds. Las contraseñas se guardan como hashes bcrypt con salt, **no cifradas reversiblemente**; los refresh tokens solo se persisten como SHA-256.

**El frontend consume autenticación real**: `features/auth/services/auth-service.ts` usa Axios contra `/api/v1` en el mismo origen público. Login y registro crean sesiones reales; el perfil público vive en React Query, no en Zustand. El workspace y onboarding tienen comprobación de sesión en servidor y gate cliente. Recargar recupera la sesión por cookies, pero descarta el progreso y los datos comerciales mock. Las contraseñas no se copian a Zustand, React Query ni almacenamiento persistente; access/refresh solo viajan en cookies HttpOnly.

La autorización actual comprueba sesión, usuario y Membership activa en el negocio; credenciales, perfil, inicio/validación de sesión y rotación excluyen filas con `isDeleted = true`, incluidos sus negocios y relaciones. Logout/revocación sí actualizan también filas eliminadas para no perder la revocación al restaurar. Esto requiere la migración `20261020170000_plural_tables_soft_delete` (tablas plurales y `isDeleted`), ya aplicada explícitamente al destino configurado sin borrar datos; ver [database.md](./database.md) para el despliegue coordinado, sin ejecución automática. El borrado lógico por sí solo no propaga revocaciones ni libera el email único. El módulo business permite actualizar solo el nombre con rol OWNER/ADMIN del negocio activo; productos ya tiene repositorio business-scoped y API de catálogo con lecturas para membresías activas y escrituras OWNER/ADMIN; los demás módulos siguen sin repositorios/endpoints comerciales ni RBAC general. Ver [products.md](./products.md). Las FK multi-tenant no sustituyen autorización.

## Endpoints implementados

Base `/api/v1`, JSON; respuestas auth `Cache-Control: no-store`. Access y refresh **nunca** se devuelven en JSON ni se guardan en localStorage. El token CSRF sí se devuelve al cliente y no sirve como credencial de autenticación.

| Método y ruta                                 | Entrada y resultado                                                                                                                                                                           |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /auth/csrf`                              | Bootstrap CSRF: `{ data: { csrfToken } }`, cookie de contexto preautenticado o vínculo a la sesión verificada.                                                                                |
| `POST /auth/register`                         | `{ name, email, password, businessName }`; crea User, Business, Membership OWNER y sesión en una transacción; 201 y perfil público.                                                           |
| `POST /auth/login`                            | `{ email, password, businessId? }`; 200 y perfil público. Comprueba pertenencia si se selecciona negocio; sin selección usa la primera membresía activa por fecha/ID.                         |
| `GET /auth/me`                                | Requiere access válido y sesión/usuario/membresía vigentes; 200 y perfil público o 401.                                                                                                       |
| `POST /auth/refresh`                          | Sin JWT en body: usa cookie refresh y CSRF; rota tokens atómicamente; 204.                                                                                                                    |
| `POST /auth/logout`                           | Revoca la sesión/familia y borra cookies; 204 idempotente, sujeto a validación CSRF.                                                                                                          |
| `POST /auth/change-password`                  | `{ currentPassword, newPassword }` estricto; access/CSRF, contraseña actual y nueva distinta; actualiza hash y revoca todas las sesiones del usuario, borra cookies; 204.                     |
| `POST /auth/change-password-with-credentials` | Público con CSRF/Origin; `{ email, currentPassword, newPassword }` estricto. Verifica credenciales, cambia hash y revoca sesiones de esa cuenta; borra cookies locales; 204. No emite sesión. |
| `POST /auth/logout-all`                       | Requiere access y CSRF; revoca todas las sesiones del usuario; 204.                                                                                                                           |

Perfil público: `{ data: { user: { id, name, email }, activeBusinessId, memberships: [{ businessId, role, business: { id, name, slug } }] } }`. Nunca incluye passwordHash, hash refresh ni otros usuarios. Errores actuales: `{ statusCode, error: { code, message } }`, mensajes genéricos sin detalles internos; los 500 registran/devuelven un identificador de incidente en `X-Request-Id`, nunca el error crudo. El normalizador Axios frontend mapea este envelope sin mostrar mensajes internos. Email normalizado en servidor. Registro exige al menos 8 caracteres (puntos de código Unicode), una letra y un número decimal Unicode; rechaza más de **72 bytes UTF-8** para evitar truncamiento silencioso de bcrypt. Login no transforma contraseñas; hash/compare son asíncronos y se usa un hash ficticio si el usuario no existe. Los errores de credenciales son genéricos; un conflicto de registro no identifica cuál campo está ocupado, aunque el estado de conflicto permite inferir disponibilidad. Verificación de email, recuperación de contraseña, MFA e invitaciones no están implementados; requieren contratos/proveedores adicionales. El cambio de contraseña sí está implementado tanto con sesión como desde login con email y contraseña actual, sin envío de email ni recuperación de cuenta.

Todos los campos password (login, registro, actual, nueva y confirmaciones) incluyen un icono Eye/EyeOff para mostrar/ocultar individualmente, con etiqueta accesible es/en y estado local inicialmente oculto. No cambia el valor ni persiste la visibilidad; el control global de cambio queda sustituido por estos botones.

## Indicador de fortaleza

Registro y los dos flujos de cambio muestran un indicador local es/en, accesible mediante `meter`, con requisitos de longitud/letra/número. No se envía ni almacena la contraseña para calcularlo. Vacío: sin contraseña; débil: no cumple la política; media: cumple; fuerte: cumple y tiene al menos 12 caracteres y un símbolo distinto de letras, números o espacios. El cómputo cuenta puntos de código Unicode; no normaliza ni recorta la contraseña. El indicador es orientativo, no calcula entropía ni consulta filtraciones: no garantiza seguridad ni bloquea una contraseña válida de nivel medio. Login y contraseña actual mantienen su validación existente para no impedir verificar credenciales anteriores. Símbolos permitidos, no obligatorios.

## Cambio de contraseña autenticado

- Pantalla `/{locale}/settings/password` dentro del workspace protegido por SSR y gate cliente. Acceso mediante llave en el header y sección Seguridad de Configuración, disponible incluso si falla la lectura de preferencias mock. Cualquier usuario con sesión vigente puede cambiar solo su propia contraseña: la identidad procede de `claims.sub`, no se acepta un ID, email ni negocio del body.
- RHF/Zod en es/en: contraseña actual, nueva y confirmación (solo cliente), mostrar/ocultar, autocomplete de gestores, bloqueo al enviar y errores de campo/API. Actual hasta 72 bytes UTF-8; nueva distinta, mínimo 8 caracteres con al menos una letra y un número decimal Unicode, máximo 72 bytes UTF-8 tanto en DTOs de API como cliente. No se transforman contraseñas. API devuelve 400 `INCORRECT_PASSWORD` si la contraseña actual no coincide; resto de validación 400, sesión inválida 401, CSRF 403 y throttling 429 (5 intentos/minuto por IP/proceso, no por cuenta).
- Bcrypt verifica la actual y genera el nuevo hash fuera de la transacción. El repositorio bloquea `Users` con `FOR NO KEY UPDATE`, vuelve a comprobar sesión/membresía/usuario/negocio vigentes y actualiza mediante comparación del hash anterior (CAS). Cambio de hash y revocación de **todas** las familias/refresh del usuario (todos sus negocios, incluida la sesión actual y filas borradas lógicamente) se confirman en una sola transacción; un fallo revierte ambos.
- Login toma el mismo bloqueo y revalida el hash comprobado por bcrypt antes de crear sesión: una autenticación iniciada con la contraseña anterior no crea una familia válida después del cambio. `NO KEY UPDATE` permite los bloqueos FK key-share del refresh; las revocaciones bloquean familias antes que tokens, como refresh. No hay retries de transacciones/mutaciones inciertas. Estos mecanismos están implementados, sin comprobación de concurrencia/runtime autorizada todavía.
- Éxito: 204 sin tokens/perfil, elimina cookies access/refresh/CSRF/preauth. El cliente vacía campos, limpia perfil/caché comercial/borradores y notifica otras pestañas por BroadcastChannel; navega a un documento nuevo en `/{locale}/login?passwordChanged=1` con aviso y exige la contraseña nueva. El query param es solo un aviso de interfaz, no prueba criptográfica del cambio. Otros dispositivos detectan la revocación al revalidar; la API rechaza sus sesiones en la siguiente petición protegida.
- El POST se ejecuta bajo el lock auth después de recuperar sesión y verificar el usuario esperado. No se usan mutations de React Query para no conservar contraseñas en sus variables/caché. Campos y petición son transitorios; no hay credenciales en Zustand ni almacenamiento persistente. Al abandonar se aborta la petición cliente, lo cual **no garantiza** rollback si el servidor ya la recibió. Ante pérdida de respuesta/5xx se vacían campos, no se reenvía automáticamente y se indica intentar login con la nueva contraseña antes de repetir el cambio. No se incluye confirmación en el body API.
- No requiere migraciones, seeds, nuevas dependencias ni proveedores. No hay reset por email, cambio administrativo de otra cuenta ni política de historial de contraseñas.

## Cambio de contraseña desde el login

- Enlace **Cambiar contraseña** en login hacia `/{locale}/change-password`, pantalla pública con el mismo shell de acceso, tema/idioma y formulario reutilizado: correo, contraseña actual, nueva y confirmación local. No necesita entrar al panel, no crea una sesión intermedia ni usa códigos/email. El cambio desde Configuración se conserva.
- `POST /api/v1/auth/change-password-with-credentials` recibe `{ email, currentPassword, newPassword }` estricto. No requiere access, pero sí bootstrap CSRF firmado y Origin/Referer permitido; el guard global mantiene CSRF incluso en rutas públicas. Límite específico de 5 intentos/minuto/IP/proceso (por endpoint, no por cuenta ni distribuido).
- Email normalizado; política de contraseña igual al cambio autenticado. Bcrypt compara incluso cuando el email no existe, con el hash ficticio existente. Email desconocido, contraseña incorrecta y usuario inactivo/eliminado responden el mismo 401 genérico sin identificar el campo ni confirmar que la cuenta exista. El frontend muestra ese error sin redirigir al login ni invalidar una sesión distinta por un intento fallido. Un hash cambiado concurrentemente también provoca 401.
- La cuenta se identifica **solo por las credenciales presentadas**, no por cookies de otra cuenta ni un ID enviado por el cliente. Permite cambiar la contraseña de un usuario activo/no eliminado aunque no tenga membresía activa: es una operación de credenciales de cuenta, no acceso a un negocio. Sigue sin permitir login a negocios no autorizados.
- Reutiliza la transacción del cambio autenticado: bloqueo de `Users FOR NO KEY UPDATE`, CAS del hash activo/no eliminado, hash nuevo y revocación de todas las familias/refresh de esa cuenta juntos. La variante con sesión mantiene además su revalidación de sesión/relaciones. Login se serializa con ambas variantes. No se emiten tokens ni se crea otra sesión.
- Éxito 204, elimina cookies del navegador actual, limpia perfil/caché/borradores y notifica pestañas; documento nuevo de login con aviso. Si el navegador tenía cookies de otra cuenta, también se eliminan localmente; sus sesiones en otros dispositivos no se revocan. Las revocaciones persistidas corresponden exclusivamente a la cuenta del email verificado.
- POST serializado bajo Web Lock con CSRF fresco, sin recuperación automática de sesión como prerrequisito y sin replay. Mantiene las mismas precauciones de abort/resultado incierto y límites de credenciales transitorias, sin Query mutation cache ni almacenamiento persistente. Ante error se conservan solo el correo y se vacían los tres campos de contraseña. No hay recuperación si se desconoce la contraseña actual; código por email queda pendiente.
- Sin cambios de esquema, migraciones, seeds, proveedores ni dependencias nuevas. Solo verificación estática/build; el comportamiento HTTP/navegador y la concurrencia siguen pendientes de autorización para pruebas.

## Flujo de consumo

1. Solicitar `GET /api/v1/auth/csrf` con cookies habilitadas (`credentials: "include"` o Axios `withCredentials: true`). Conservar `data.csrfToken` solo en memoria.
2. Enviar registro/login con `Origin` permitido, JSON y `X-CSRF-Token`; el navegador adjunta las cookies del bootstrap.
3. Tras autenticarse se invalidan CSRF y pre-sesión anteriores: solicitar **otro** `/auth/csrf` antes de mutar, refrescar o salir. `/auth/me` usa access y no necesita header CSRF por ser lectura.
4. Refresh exige la cookie refresh, el CSRF ligado a la misma sesión y Origin permitido. No requiere access vigente. La sesión estable conserva el vínculo CSRF entre rotaciones hasta que expire el propio CSRF.
5. Logout requiere CSRF válido; después elimina todas las cookies auth. Repetir logout requiere nuevo bootstrap si ya se borraron. Logout-all requiere además access válido.

Para herramientas no navegador, enviar cookies, Origin permitido y CSRF explícitamente. CORS por sí solo no autoriza solicitudes. No se han ejecutado peticiones de ejemplo ni pruebas de runtime por la restricción vigente.

## Cookies y topología

Host-only, sin `Domain`, `Path=/`, `HttpOnly`, `SameSite=Lax`. Producción añade `Secure` y nombres `__Host-access`, `__Host-refresh`, `__Host-csrf`, `__Host-preauth`. En HTTP de desarrollo usa `dev-access`, `dev-refresh`, `dev-csrf`, `dev-preauth`. La eliminación reutiliza los atributos originales. La cookie CSRF es HttpOnly: el cliente obtiene el valor mediante el JSON del bootstrap.

Web/API usan el **mismo origen público**: un rewrite de Next reenvía `/api/v1/:path*` a `API_INTERNAL_URL` (privada, por defecto `http://localhost:8000/api/v1`, también usada por SSR). El navegador nunca llama directamente al host interno; el proxy conserva cookies y `Set-Cookie`. Configurar `CORS_ORIGINS` en Nest con el origen público exacto de la web. La URL interna participa en la clave de build de Turbo: cambiarla requiere rebuild; los despliegues pueden sustituir el rewrite por un reverse proxy equivalente. No reenviar credenciales a una URL arbitraria: se valida como HTTP(S) sin usuario/clave/query/hash. Producción exige HTTPS público y API en `NODE_ENV=production` para las cookies Secure/`__Host-`. Hosts separados o realmente cross-site no están soportados por esta integración; nunca asumir que sus cookies llegan a Next.

## Tokens y sesiones persistidas

- jose firma/verifica HS256 con secretos independientes access/refresh; algoritmo permitido, issuer, audience, propósito, expiración, `sub`, `jti`, `sid` y `businessId` comprobados. Ninguna clave se obtiene de URLs del token. Roles y pertenencia se consultan en servidor.
- `AuthSession` es la familia estable revocable: usuario/negocio, expiración absoluta e inactividad. `RefreshSession` representa cada refresh emitido: hash SHA-256, `jti` como ID, familia, expiración, consumo y revocación.
- Valores por defecto: access **15 minutos**, inactividad refresh **7 días**, límite absoluto de sesión **30 días**, CSRF **1 hora**, bcrypt **12 rondas**. Configurables en `.env.example`; access < refresh <= sesión. Renovar extiende inactividad, nunca el límite absoluto; expiración de tokens acotada por la sesión.
- Refresh bloquea la familia con `SELECT ... FOR UPDATE`, comprueba vigencia/pertenencia, consume el token y crea el sucesor en una transacción. El rechazo por reutilización conserva el commit de revocación. Se guardan registros consumidos para detectar replay; no borrar esa evidencia antes de vencer la familia.
- Política estricta: **refresh simultáneo o reutilizado revoca la familia**. Coordinar un solo refresh entre solicitudes/pestañas; no reintentar automáticamente una renovación incierta o con respuesta perdida.
- Guards consultan estado de sesión y Membership en cada petición protegida: logout revoca también access aún no expirado. El guard global protege por defecto las rutas salvo metadata pública explícita; `GET /` del starter también queda protegido y no es un health check.

## CSRF, límites y configuración

Mutaciones verifican Origin exacto contra `CORS_ORIGINS`, o Referer controlado si falta Origin; sin ninguno se rechazan. CSRF usa **double-submit firmado con HMAC**, header `X-CSRF-Token` y cookie coincidentes, con caducidad y vínculo criptográfico a sesión/pre-sesión. No se combina con un almacén ficticio de tokens sincronizados. SameSite y CORS son defensas adicionales, no sustitutos.

Cuerpo HTTP máximo 16 KiB. Throttler global y límites específicos para registro/login/bootstrap/refresh/cambio de contraseña; almacenamiento **en memoria por proceso e IP**, no por cuenta ni distribuido. No se confía automáticamente en `X-Forwarded-For`; desplegar detrás de proxy requiere definir IP confiable y límites de borde/almacén compartido. Una IP de proxy compartida puede agotar el límite de todos sus clientes. Ajustar y verificar antes de producción.

`AUTH_ACCESS_SECRET`, `AUTH_REFRESH_SECRET`, `AUTH_CSRF_SECRET`: obligatorios, distintos, mínimo 64 caracteres. Ejecutar `pnpm --filter @whatsapp/api auth:configure` para generar los que faltan en el `.env` local, sin imprimirlos ni sobrescribir valores existentes. En producción usar gestor de secretos, HTTPS, TLS verificado hacia PostgreSQL y un plan de rotación; la implementación actual no ofrece keyring/`kid` para rotación sin invalidar tokens. Cambiar secretos invalida los tokens firmados con los anteriores.

## Integración Next.js implementada

- Formularios RHF/Zod es/en: login envía email/password; registro añade nombre del usuario y negocio, confirmación solo local y límites alineados con bcrypt (8 caracteres mínimo, al menos una letra y un número decimal Unicode, 72 bytes UTF-8 máximo). Los errores distinguen validación, 401, conflicto, CSRF, límite y conexión; no hay cuentas ni errores simulados.
- CSRF se obtiene antes de cada mutación y de nuevo tras login/registro; solo se conserva en variables en memoria. No hay interceptor que reenvíe indiscriminadamente mutaciones, ni retries de login/register/refresh/logout/change-password. Tras renovar solo se repite `/auth/me` una vez.
- `auth-service.ts` serializa TODAS las operaciones auth con Web Locks del mismo origen (también entre pestañas). Antes de renovar vuelve a comprobar `/auth/me` dentro del lock; otro consumidor puede haber renovado mientras esperaba. El polling del perfil es cada 60 s mientras la pestaña está visible; también se revalida al recuperar conexión y tras eventos de otras pestañas. Recuperar el foco o volver a una pestaña visible no invalida manualmente la sesión; `refetchOnWindowFocus` permanece desactivado.
- Antes de enviar refresh se guarda **solo una marca booleana de incertidumbre** en localStorage, nunca JWT, CSRF, contraseñas o perfil. Se elimina tras un perfil válido de `/me`, un refresh exitoso o un nuevo login/registro/logout exitoso; un refresh rechazado también la conserva de forma conservadora. Si se pierde la respuesta, no se reintenta refresh automáticamente, incluso tras recargar; se pide volver a iniciar sesión. Sin Web Locks o sin almacenamiento disponible se desactiva renovación automática de forma conservadora. Esto puede exigir relogin al expirar access; no garantiza continuidad offline.
- `server-session.ts` lee cookies bajo un `Suspense` padre y consulta `/auth/me` con `cache: "no-store"`, timeout y solo las cookies access conocidas. No renueva ni escribe cookies desde Server Components. Si falta/expira access, una recuperación cliente renueva y luego solicita un nuevo render del servidor; si la API falla muestra error/reintento sin renderizar el área protegida. Cache Components y partial prerender conservan únicamente el fallback público, no el contenido autenticado.
- `SessionGate` mantiene `SessionStatus` tanto en SSR como durante la hidratación inicial mediante el snapshot servidor de `useSyncExternalStore`; solo después consulta el estado visual de React Query. Así, si `/me` se resuelve antes de hidratar el límite de streaming (por ejemplo al volver de Facebook Login), la caché cliente no cambia el HTML inicial. No se suprimen avisos de hidratación ni se desactiva SSR. `SessionGate` no entrega el shell ni onboarding sin un perfil verificado. El guard API sigue siendo la autoridad; la redirección de idioma o de acceso no sustituye autorización. Login va a dashboard y registro a onboarding; el registro ya creó Business antes del wizard, que reutiliza ese Business y su nombre de `/me`. Al finalizar envía `PATCH /businesses/:businessId` con solo `{ name }`, bajo el mismo Web Lock: recupera sesión antes de mutar, verifica identidad/negocio esperados y obtiene CSRF. La mutación nunca se reenvía automáticamente; un error de red puede dejar resultado incierto. React Query actualiza el nombre confirmado y revalida `/me`. Después se guarda también nombre, tono e instrucciones del agente con el PUT de configuración general, conservando saludo/habilitado existentes o creando un agente deshabilitado con saludo inicial. Ambas escrituras son independientes; si falla el agente se informa del guardado parcial y se conserva el borrador sin navegar ni marcar completado. Ver [agents.md](./agents.md). Descripción, tienda, WhatsApp, progreso y marca de completado continúan solo en memoria.
- Logout y logout-all en el header, avisos BroadcastChannel y revalidación por conexión, limpieza de React Query comercial, repositorio mock, escenarios y borradores al salir/cambiar identidad/perder sesión. El estado visual de tema/sidebar se conserva. El cierre de todas las sesiones en otros dispositivos se detecta al volver a validar, no por push.

## Pendiente y verificación

Productos tiene permisos acotados de escritura OWNER/ADMIN y datos separados por usuario/negocio en React Query; no hay selección de negocio ni RBAC comercial general en frontend; `activeBusinessId` y memberships proceden del servidor. No reintentar futuras mutaciones comerciales no idempotentes ni usar una redirección frontend como autorización. Ver [estado y próximos pasos](./login-plan.md).

Auditoría durable sin secretos, limpieza programada de sesiones, límites distribuidos/por cuenta, recuperación/verificación de email, políticas RBAC comerciales, observabilidad y verificaciones de seguridad siguen pendientes. No declarar listo para producción: por instrucción del usuario **no se implementaron ni ejecutaron tests, smoke checks, peticiones HTTP ni comprobaciones de navegador**. Lint, formato, tipos y build no prueban seguridad ni comportamiento de las sesiones.
